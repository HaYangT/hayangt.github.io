# 개요
면접준비와 다양한 요인으로 인해 바빠 글을 늦게 적게 되었다. 게을러진거 같아 반성하게 된다.

이번에는 기업의 요구사항을 받아 프로젝트를 만드는 기업연계 프로젝트에 참가하게 되었다. 프로젝트는 심전도 데이터를 받아 사전에 환자의 발작을 예측하여 방지하는 소프트웨어의 개발이다. 이 프로젝트로 많은 것을 배운 만큼, 정리할 것도 많을 것 같다.

---


## 심전도에 대한 이해
개발에서 가장 중요한 것은 도메인 지식이라고 생각한다. 특히 데이터 관련 담당을 맡게된 나는 심전도와, 거기서 알 수 있는데 데이터에 대해 공부를 하게 되었다.
다행히도 여동생이 메디컬이라 관련된 지식을 배울 수 있었다.

우리가 추출하는 특징은 약 17개 가량이였는데, Time Domain, Frequency Domain, NonLinear Domain 3가지로 나뉜다.

Time Domain의 데이터는 연속되는 수치들 사이에서 추출되는 값으로, 심박사이의 간격과 관련된 데이터들이다.
Frequency Domain은 심박 변화를 주파수 성분으로 분해한뒤, 특정 지표의 균형 값들이다.
NonLinear Domain은 심장 리듬의 복잡성, 혼돈성(비일관성)을 분석하여 리듬의 구조를 값으로 나타낸 것이다.

해당 지표들은 모두 ECG(심전도)데이터에서 추출 할 수 있었고, 이를 도와준 것이 Neurokit2라는 오픈소스다.

## 생체 특징 추출 오픈소스 Neurokit2
Neurokit2는 인간의 생체신호에서 특징을 추출하는 파이썬 라이브러리다. 데이터 전처리, 특징 추출이 주 기능이며, 이를 사용하는걸 권장하여 배우게 되었다.

Neurokit2, 뉴로킷은 세 개의 계층으로 구성되어 있다.

### 저수준
신호 처리를 위한 기본적인 기능들이다.

- **signal_filter()**
원시 신호에서 노이즈를 제거하는 함수. 다양한 필터링 알고리즘을 포함하며,  **method** 인수(파라미터)만 바꾸면 필터 종류를 전환할 수 있다. 저역통과, 고역통과, 대역통과 등 주파수 대역도 매개변수로 지정 가능하며, 필터 차수**(order**)도 조절 가능하다.
- **signal_interpolate()**
불규칙하게 샘플링된 데이터 포인트 사이를 채우는 보간 함수. 심박수처럼 R-Peak 간격에서 비정기적으로 추출된 값을 연속적인 시계열로 변환할 때 주로 쓰인다. 선형, 스플라인, 최근접 이웃 등의 보간 방법을 선택할 수 있음.
- **signal_resample()**
신호의 샘플링 레이트를 변환.
예시) 1000Hz로 기록된 ECC와 256Hz로 기록된 EDA를 함께 분석하기 위해 동일한 샘플링 레이트로 맞춰야함.
이 함수가 그 역할을 한다.
- **signal_detrend()**
신호에서 느리게 변하는 추세를 제거함. 생체 신호 기록 중 전극 접촉 변화나 땀 등으로 기저선이 서서히 이동하는 경우가 많지만, 다항식 제거나 **타르발 방법(**전체적으로 느리게 변하는 흐름을 제거해서 진짜 변동성만 분석하게 해주는 방법**)**등을 통해 추세를 제거하고 실제 관심 있는 신호 변동만 남긴다. ****
- **singal_findpeaks()**
신호에서 피크를 탐지함. R-Peak와 같은 신호를 탐지하며, 최소 높이, 최소 간격 등의 매개변수를 조절하여 감도를 설정할 수 있다.

### 중수준
저수준 함수들을 특정 생체 신호에 맞게 조합해 놓은 함수들이다. 뉴로킷은 어떤 생체신호를 다루던 동일한 패턴의 함수 이름을 사용한다. 예를 들어 클리닝 작업을 진행할때 ECG는 ecg_clean(), EDA는 eda_clean()을 사용한다.

- ***_clean()**
원시 신호에서 노이즈와 아티팩트를 제거한다.
- ***_findpeaks()**
해당 신호에서 의미 있는 피크를 찾는다.
- ***_rate()**
피크 간격으로 부터 심박수나 호흡수 같은 비율을 계산한다.
- ***_phase()**
신호의 주기적 위상을 분류한다.
- ***_process()**
위 단계들을 순서대로 묶어서 한번에 실행한다.
- ***_plot()**
처리 결과를 시각화한다.

같은 함수를 호출하더라도 내부적으로 호출하는 저수준 함수의 설정이 다르기 때문에 내부 동작이 다르다. 예를 들어 근육 활동 신호는 고주파 성분이 중요하기 때문에 넓은 주파수 대역을 사용하고, 피부 전도는 매우 느리게 변하기 때문에 저역통과 필터를 사용한다.

중수준 계층의 가장 강력한 특징 중 하나는 method 인수인데, method = "논문명" 으로 지정해두면, 해당 논문에서 제안한 필터링 설정이 자동으로 적용된다. 다양한 논문의 파이프라인들을 변수 값만 바꿔가면서 쉽게 비교할 수 있다.

하지만 method에 내장된 옵션들이 우리의 프로젝트와 맞지 않는 경우도 있다. 그럴 땐 직접 저수준 함수들을 조합할 수 있다. 이러한 자유도가 뉴로킷을 사용하는 이유중 하나이기도 하다.

### 고수준
중수준 함수들을 올바른 순서로 자동 연결해주는 파이프라인이다. 단 하나의 함수 호출로 모든 과정을 진행할 수 있다.

ecg_process(method ="neurokit")이라는 함수를 예로 들면, 해당 함수는 다음과 같이 실행된다.

1. **ecg_clean()** 함수가 원시 ecg 신호에서 노이즈를 제거한다. ****
2. 다음으로 **ecg_peaks()**가 클리닝된 신호에서 R-Peak를 감지한다
3. **ecg_quality()** 가 감지된 신호의 품질을 평가하여 아티팩트나 노이즈가 심한 구간을 표시한다
4. **ecg_delinate()** 가 R-Peak 뿐안 아니라 P파,Q파,S파,T파 등 심전도의 세부 구성 요소를 식별한다.
5. **ecg_phase()**가 각 시점이 수축기인지 이완기인지 분류한다.

method 인수를 고수준 함수에서 정의하면, 하위에 있는 모든 중수준 함수에 일괄 전달된다. 이를 통해 서로 다른 method를 적용하여 결과들을 비교할 수 있다.

## 병목을 해결해보자
서비스 파이프라인에서 Neurokit2를 사용하는 부분의 시간이 다른 곳에 비해 많이 느린것을 발견했다. 스트레스 테스트를 진행하던 도중 몇몇 세션이 타임아웃이 발생하여 살펴본 결과, 데이터 전처리와 특징 추출에서 많은 시간이 소요되는 것을 발견했다.
최적화 할 방법을 떠올려 보던 도중, 문득 PS를 하며 파이썬이 다른 언어에 비해 느리다는 것이 떠올라 그 이유를 찾아보기로 했다.

파이썬에서 가장 널리 사용되는 구현체인 CPython은 소스 코드를 바이트코드로 변환한 뒤 인터프리터를 통해 실행한다. 또한 파이썬은 동적 타입 언어이기 때문에 연산이 실행될 때 객체의 타입과 수행할 연산을 결정한다.
이러한 특성은 개발 편의성과 유연성을 제공하지만, 반복 횟수가 많은 수치 계산에서는 적지 않은 오버헤드를 만든다. 특히 파이썬의 for 문 내부에서 계산을 수행하면 매 반복마다 바이트코드 해석, 타입 확인, 객체 생성 및 참조 관리가 반복된다.

```python
result = []

for value in signal:
    result.append(calculate_feature(value))
```

데이터의 크기가 작을 때는 이러한 비용이 크게 드러나지 않았지만, 긴 생체 신호를 처리하거나 동시에 많은 연산을 수십만 번 반복하면 파이썬 인터프리터의 오버헤드가 누적되어 전체 처리 시간에 영향을 줄 수 있다.


### Numba JIT 적용
이 문제를 개선하기 위해 병목으로 확인된 반복 계산에 Numba의 JIT 컴파일을 적용했다.

Numba는 함수가 처음 호출될 때 파이썬과 Numpy로 작성된 코드를 기계어로 컴파일 한다. 이후 호출에서는 인터프리터를 거치지 않고 컴파일된 코드를 실행하기 때문에, 반복문과 수치 연산이 많은 코드에서 성능 향상을 기대할 수 있다.

```python
import numpy as np
import numba as nb


@nb.njit(cache=True)
def mwa(signal: np.ndarray, window_size: int) -> np.ndarray:
    """이동 평균 (causal). 초기 구간은 실제 샘플 수로 나눔."""
    n = len(signal)
    out = np.empty(n)
    cumsum = 0.0

    for i in range(n):
        cumsum += signal[i]

        if i < window_size:
            out[i] = cumsum / (i + 1)
        else:
            cumsum -= signal[i - window_size]
            out[i] = cumsum / window_size

    return out
```
일반적인 파이썬 코드에서는 루프를 순회할 때마다 타입과 연산을 확인해야하는 반면, Numba는 입력값의 타입을 기반으로 함수를 컴파일하고, 루프를 네티이브 코드로 실행한다.
이를 통해 많은 반복 처리 비용을 상당 부분 제거할 수 있다.

하지만, Numba는 숫자형 배열을 대상으로 하는 반복문과 수치 계산에 효과적이기 때문에, 사용할 수 있는 부분이 제한적이다.

## 파이프라인과 ERD
서비스의 데이터 처리 파이프라인은 여러 단계와 테이블로 구성되어 있어, 전체 흐름과 데이터 간 관계를 명확히 정리할 필요가 있었다.

먼저 사용자가 측정을 시작하면 서버에 session이 생성된다. session은 ECG 측정 기간을 나타내는 논리적인 단위다. 생성된 세션은 사용자가 종료를 요청하거나 타임아웃이 발생할 때까지 활성 상태를 유지한다.

활성화된 세션에서 사용자는 ECG 데이터를 10초 단위로 서버에 전송한다. 서버는 각각의 신호 조각을 signal이라는 객체로 추상화하고, 소속 세션과 순서를 확인할 수 있도록 session_id와 seq_no를 함께 저장한다.

수신된 신호는 Redis의 슬라이딩 윈도우에 순서대로 누적된다. 신호의 개수가 설정된 윈도우 크기인 redis_signals_max_count에 도달하면 하나의 분석 구간이 완성되고 전처리를 시작한다. 이 분석 구간을 데이터베이스에서는 batch로 표현하며, batch_duration에는 해당 윈도우의 전체 길이를 저장한다.
실제 구현에서는 신호가 수신될 때 signal과 후보 batch를 함께 생성한다. 이후 윈도우가 완성되면 가장 최근에 생성된 batch를 해당 분석 구간의 식별자로 사용하고, 윈도우에 포함된 신호들을 연결한다.

슬라이딩 윈도우 방식에서는 하나의 signal이 여러 batch에 포함될 수 있고, 하나의 batch 역시 여러 signal을 포함한다. 따라서 두 객체는 N:M 관계이며, 이를 표현하기 위해 중간 테이블인 batch_signal을 두었다. batch_signal에는 두 객체의 식별자뿐 아니라 배치 내부에서의 신호 순서를 나타내는 seq_no도 함께 저장한다.

윈도우가 완성되면 해당 batch를 대상으로 잡음 제거, 리샘플링 등의 전처리를 수행한다. 전처리 결과와 특징 추출 결과는 서로 다른 시점에 생성되고 각각 별도의 상태와 메타데이터를 가지므로, preprocessing과 feature 테이블로 분리했다. 두 테이블은 모두 batch.id를 공유 기본 키로 사용하여 batch와 1:1 관계를 형성한다.

추출된 feature는 예측에 사용된다. 예측 단계 역시 여러 개의 특징 데이터를 사용하는 슬라이딩 윈도우 방식이다. 하나의 predict_result는 여러 feature를 사용하고, 하나의 feature도 서로 겹치는 여러 예측 윈도우에 재사용될 수 있다. 따라서 두 테이블은 N:M 관계이며, 이를 관리하기 위해 predict_feature 중간 테이블을 두었다.

이러한 구조를 설계하면서 고민했던 부분은 계층이 깊어질수록 특정 데이터의 처리 이력을 조회하기 위해 여러 번의 JOIN이 필요하다는 점이었다. 프로젝트에서는 원본 신호부터 전처리, 특징 추출, 예측 결과까지의 추적성이 중요했기 때문에 관련 데이터를 자주 조회해야 했다.

이에 따라 predict_result.session_id나 batch_signal.seq_no처럼 조회에 자주 사용되는 값을 일부 하위 테이블에 중복 저장하는 반정규화를 적용했다. 그 결과 저장 공간 사용량과 데이터 정합성 관리 부담은 다소 증가했지만, 자주 사용되는 조회 경로에서 불필요한 JOIN을 줄이고 데이터의 소속과 처리 순서를 빠르게 확인할 수 있었다.

## 마무리

SSAFY에서 진행한 마지막 프로젝트였던 만큼, Caredio에는 이전 프로젝트보다 더 많은 고민이 담겼다. 이번에는 저번과 달리 요구사항을 단순히 기능으로 구현하는 데서 끝나지 않고, 요구사항이 필요한 이유를 확인하고 기업 담당자와 반복적으로 소통하며 설계의 기준을 세워 나갔다.

특히 추적성은 단순히 로그를 많이 남기는 것만으로 확보되는 것이 아니었다. 세션에서 시작해 신호, 배치, 전처리, 특징 추출, 예측 결과로 이어지는 데이터 구조와 각 단계의 상태, 실패 기록과 복구 흐름까지 함께 설계해야 했다. 이를 통해 관측 가능한 시스템은 구현 이후에 덧붙이는 기능이 아니라, 설계 단계부터 고려해야 하는 특성이라는 것을 배웠다.

면접 준비와 예비군 등 일정상 여러 우여곡절이 있었지만, 팀원들과 끝까지 프로젝트를 완성할 수 있었다. 
SSAFY의 마지막 프로젝트를 이러한 경험으로 마무리할 수 있어 좋았다.
